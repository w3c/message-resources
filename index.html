This specification defines a standard container for localizable content, especially messages that support Unicode MessageFormat [[CLDR]].

Introduction

This specification defines a container for messages, including a data model, file-based serialization, and basic processing.

Message resources allow application and document format authors to separate strings and other content that might need localization from the logic and presentational structure of Web content. This includes (but is not limited to) HTML pages, scripts, manifests, or other documents. This allows for the creation, translation, or adaptation to new languages or locales without affecting the core functionality and fascilitates management of presentation to audiences that vary by language or culture.

Terminology

This section contains terminology specific to this document.

Much of the terminology needed to understand this document is provided by the Internationalization Glossary [[I18N-GLOSSARY]]

Message. In this document's context, a "message" refers to a specific message format pattern string, including additional data or metadata relating to the message's handling or localization.

A message format pattern string can be a plain string that requires no formatting at all, including the empty string.

Unicode MessageFormat ("MF2") is a Unicode Consortium standard defined as part of [[UTS35]] that defines the data model, syntax, processing, and conformance requirements for the next generation of dynamic messages.

Message Resource Structure

The syntax of a message resource document is defined by this section using [[ABNF]], along with a non-normative corresponding TypeScript data model.

The design of the message resource syntax is inspired by multiple other pre-existing syntaxes, and is intended to be understandable without prior experience.

The overall structure is quite similar to [[?TOML]] and other INI-like file formats, combined with a resource-head that's close to the "frontmatter" used by many markdown processors. The syntax for contextual comments and metadata, including the use of the `@` prefix sigil, is drawn from the conventions used by [[JavaDoc]] and [[JSDoc]] comments on functions.

Resource

A message resource consists of a resource-head followed by any number of section headers, entries, comments and empty lines.

A message resource MUST contain a resource-head, but it MAY be otherwise empty.

        resource = resource-head *(newline item)
Resource Data Model

A `Resource` is the root of the data model representation of a message resource. Its `Resource.comment` and `Resource.meta` values are set by [[[#resource-head|`resource-head`]]] contents, while `Resource.sections` represents the remaining contents of the message resource.

          interface Resource {
            comment: string;
            meta: Metadata[];
            sections: Section[];
          }

The data model is not a concrete syntax tree, and so does not encode whitespace or empty lines. Users are encouraged to consider them not significant, and to always normalize the syntax representation of a message resource when manipulating it programmatically.

Resource-Head

Comments and metadata before the `---` separator relate to the entire resource.

The resource-head cannot be empty, as at least the `@locale` metadata is REQUIRED.

A resource MUST NOT have any section-head or entry items before the `---` separator.

        resource-head = *((comment / empty-line) newline)
                        1*(metadata newline)
                        "---" [ws]

Comment

Comments within the resource-head always attach to the resource as a whole. In the resource body, comments attach to a subsequent section-head or entry, if not separated from it by any empty lines. Metadata lines are valid between comments and their target.

Comments that attach to the resource, a section-head, or an entry are considered to be relevant context for translation. Comments outside the resource-head that are followed by one or more empty lines are standalone comments, and MUST NOT be considered relevant for translation.

Adjacent comment lines should be considered as a single multi-line comment. To parse the value of one or more comments into a single string, the `#` sigil and up to one space or tab is trimmed from the start of each line, and any trailing whitespace is similarly trimmed. The lines are concatenated by ␤U+000A END OF LINE characters, excluding any leading or trailing empty lines. Escaping is not supported for comment values.

        comment = "#" *(content / backslash)
Comment Data Model

In the data model, attached comments are presented as `Resource.comment`, `Section.comment`, and `Entry.comment` string values. Standalone comments are presented as `Comment` values. An empty or whitespace-only comment will be represented by an empty string.

          interface Comment {
            type: "comment";
            comment: string;
          }

Metadata

Metadata attaches properties to the resource-head, section-head or entry. Other metadata lines are valid between metadata and its target, but comments and empty lines are not.

The `value` of `metadata` is optional. If it is not present, its parsed value is considered to be an empty string.

        metadata = "@" id-part [ws value]
Metadata Data Model

The data model representation of metadata is as an array of `Metadata` values. This allows for their relative order to be retained, and for the same `Metadata.key` value to be repeated.

          interface Metadata {
            key: string;
            value: string;
          }

Item

Within the main body of the resource, all items are separated from each other by ␤U+000A END OF LINE or ␍␤ U+000D CARRIAGE RETURN + U+000A END OF LINE line endings. Except for empty lines, all items start with a non-whitespace character.

        item = section-head / entry / comment / empty-line

Section-Head

As in [[?TOML]], entries after a section-head belong to that section. Sections do not nest under preceding sections, and instead always define their full identifier. Section-heads may be preceded by metadata, which MUST NOT be separated by empty lines.

The normalized identifier of a section-head is a non-empty list of non-empty strings parsed from its `id` value. Each section-head MUST have a distinct normalized identifier among all section-heads and entries.

        section-head = *(metadata newline)
                       "[" [ws] id [ws] "]" [ws]
Section Data Model

The `section-head` and the [[[#entry|`entry`]]] and standalone [[[#comment|`comment`]]] values that follow before the next `section-head` are collected into the `Section` data model.

The normalized `section-head` identifier is stored as the `Section.id` array of strings. The top-level or anonymous section has an empty `Section.id` array.

The `Section.comment` value is set from `comment` lines that immediately precede the `section-head`.

          interface Section {
            comment: string;
            meta: Metadata[];
            id: string[];
            entries: (Entry | Comment)[];
          }

The message resource syntax requires the `id` array to be non-empty for all sections after the first one, but empty identifier arrays are also otherwise possible when this data model is used to represent other message resource formats, such as [[Fluent]] FTL files.

Entry

Entries may be preceded by metadata, which MUST NOT be separated by empty lines.

The normalized identifier of an entry is a non-empty list of non-empty strings parsed from its `id` value, appended to the normalized identifier of its preceding section-head (if any). Each entry MUST have a distinct normalized identifier among all section-heads and entries.

To parse the `value` of an `entry`, its parsed string value is further parsed as a Unicode MessageFormat message.

        entry = *(metadata newline)
                id [ws] "=" [ws] value
Entry Data Model

In the data model, the `Entry.id` value is a non-empty list of non-empty strings parsed from the `id` of the `entry`, but not including its section identifier. To determine the normalized identifier of an `Entry`, append `Entry.id` to its parent's `Section.id`.

The `Entry.comment` value is set from `comment` lines that immediately precede the `entry`.

          interface Entry {
            type: "entry";
            comment: string;
            meta: Metadata[];
            id: string[];
            value: Message;
          }

Identifier

An identifier is made up of one or more non-empty parts separated by `.` Full Stop characters. Common symbols and non-printable characters must be escaped.

The parsed value of an `id` is a non-empty list of non-empty strings, formed from the parsed values of each `id-part`. The parsed value of an `id-part` is the concatenation of its `id-char` and parsed `escaped` and `symbol` values. The parsed value of an escaped `symbol` is the `symbol` character.

        id = id-part *([ws] "." [ws] id-part)
        id-part = 1*(id-char / id-escape)
        id-char = ALPHA / DIGIT / "_" / "-"
                / %x00A1-1FFF / %x200C-200D / %x2030-205E / %x2070-2FEF
                / %x3001-D7FF / %xF900-FDCF / %xFDF0-FFFD / %x10000-EFFFF
        id-escape = backslash (escaped / symbol)
        symbol = %x21-2F / %x3A-40 / %x5B-60 / %x7B-7E ; ASCII symbols and punctuation
               / %xA1-BF / %xD7 / %xF7 ; Latin-1 symbols and punctuation
               / %x2010-2027 / %x2030-205E / %x2190-2BFF ; General symbols and punctuation

Value

The `value` is used in both `entry` and `metadata`.

A `value` may extend over multiple lines, as long as each line after the first is indented by at least one space or tab or is empty. If a `value` line starts or ends with significant whitespace, escape the first or last character of the line with a \U+005C REVERSE SOLIDUS. When a newline occurs in a `value`, it is always considered to represent a single ␤U+000A END OF LINE character. To include a ␍U+000D CARRIAGE RETURN character in a value, escape it as `\r`.

To parse the `value` as a string, any leading and trailing unescaped whitespace is trimmed from each line. The lines are concatenated by ␤U+000A END OF LINE characters, excluding any leading or trailing empty lines. Finally, all character escapes are parsed. The parsed values of the `\\`, `\{`, `\|`, and `\}` escape sequences are their string values, including the \U+005C REVERSE SOLIDUS.

        value = value-line *(1*newline ws value-line)
        value-line = [(value-start / value-escape) *(content / value-escape)]
        value-start = %x21-5B ; omit C0 controls, SP, and \
                    / %x5D-7E ; omit C1 controls
                    / %x00A0-2027 ; omit LSEP & PSEP
                    / %x202A-D7FF ; omit surrogates
                    / %xE000-10FFFF
        content = SP / HTAB / value-start
        value-escape = backslash (escaped / "{" / "|" / "}")

Each of the escape sequences recognised by Unicode MessageFormat pass through resource parsing as complete and intact, so that they do not need to be double-escaped.

Escaped Characters

Most escape sequences are shared between `id-escape` and `value-escape`.

The parsed value of an escaped newline (which MUST be followed by non-empty whitespace) is an empty string. This allows for line breaks to be inserted into an `id` or `value` for presentation only, and for long keys and values to be wrapped for legibility.

The parsed value of an escaped ␉U+0009 CHARACTER TABULATION or ␠U+0020 SPACE is the character itself.

The parsed value of an escaped `\n` is the ␤U+000A END OF LINE character.

The parsed value of an escaped `\r` is the ␍U+000D CARRIAGE RETURN character.

The parsed value of an escaped `\t` is the ␉U+0009 CHARACTER TABULATION character

The parsed value of the `\x`, `\u`, and `\U` escapes is the Unicode character represented by their hexadecimal values.

        escaped = backslash
                / (newline ws)
                / SP / HTAB
                / %s"n" / %s"r" / %s"t" ; represent LF, CR, HTAB
                / (%s"x" HEXDIG HEXDIG)
                / (%s"u" HEXDIG HEXDIG HEXDIG HEXDIG)
                / (%s"U" HEXDIG HEXDIG HEXDIG HEXDIG HEXDIG HEXDIG)
        backslash = "\"

The syntax allows for the same character to be escaped with more than one representation. For example, each of the these is a valid escaped form of ␉U+0009 CHARACTER TABULATION: `\`␉, `\t`, `\x09`, `\u0009`, `\U000009`.

Whitespace

The only horizontal whitespace characters that are considered as such are the ␉U+0009 CHARACTER TABULATION and ␠U+0020 SPACE characters

Both ␤U+000A END OF LINE and ␍␤ U+000D CARRIAGE RETURN + U+000A END OF LINE are accepted as line endings, but all parsed values will normalize their representation as only ␤U+000A END OF LINE characters. To include other vertical whitespace characters in a `value`, they must be escaped.

        empty-line = [ws]
        ws = 1*(SP / HTAB)
        newline = CRLF / LF
